## Open — confirmed bugs, not yet fixed (external ChatGPT review of 1.6.0, verified against code 2026-07-21)

Tagged `GPT-01` through `GPT-11` to avoid colliding with the original report's `F-01`-`F-14` numbering. Every item below was independently traced through the actual code before being added here - line numbers match what the reviewer cited. GPT-01/04/11 are fixed - see "Fixed, awaiting live-hub testing (1.6.1)" below.

- **GPT-02 (High) - power-on for level/colour commands depends on Hubitat's cached switch state, not the bulb's real state.** `sendPowerOnIfNeeded()` (`apps/LIFX_Light_Manager.groovy:2740-2748`) skips sending `SET_POWER` on whenever `child.currentValue('switch')` already says `on`. If the light was turned off outside Hubitat (LIFX app, physical control, another controller) since the last refresh, a subsequent level/colour/CT command changes HSBK but never re-powers the bulb - while Hubitat still optimistically publishes `switch: on`. **Decision (2026-07-21): accepted as a known trade-off, not fixed.** Sending power-on unconditionally on every level/colour command adds one more packet per command, and this app has a documented history of a real hub crash from LAN traffic overload. Consistent with how colour-mode staleness is already only reconciled on refresh/poll, not every command - documented in code, not silently left unaddressed.
- **GPT-03 (High) - Breathe/Pulse with a 0% base and a brighter target never becomes visible.** `runColorEffect()` (`apps/LIFX_Light_Manager.groovy:3215-3247`) only sends power-on when `baseLevel > 0` (line 3226), so an effect meant to fade in from off stays dark the whole cycle, since `SET_WAVEFORM` doesn't itself power the bulb on. Separately, the optimistic `switch` event (line 3242) is derived purely from `baseLevel`, not from whether the bulb was already on beforehand - so a light already on before the effect started can show `switch: off` in Hubitat while it's visibly breathing/pulsing. Planned for 1.6.2.
- **GPT-05 (Medium) - the LIFX-advertised UDP service port is parsed but discarded; every device is hardcoded to port 56700.** The `STATE_SERVICE` case (`apps/LIFX_Light_Manager.groovy:1233-1235`) only increments a stats counter and never reads the payload; `dev.port`/`c.port` are hardcoded to `LIFX_PORT` in three places instead. Every real LIFX device I'm aware of uses 56700 in practice, so this is spec-correctness rather than an observed active bug today. Planned for 1.6.3.
- **GPT-06 (Medium) - the fast unicast command path builds protocol-tagged/broadcast-style packets instead of properly-addressed unicast ones.** `buildZeroTargetTaggedPacket()` (each local driver, e.g. `drivers/LIFX_Local_Colour_Driver.groovy`) sets the LIFX header's `tagged` bit and zeroes the 8-byte target field, relying on IP-level unicast addressing to reach only one device rather than the protocol's own addressing. **Decision (2026-07-21): accepted as-is, not fixed.** Works reliably in practice - this exact path has been live-tested extensively all session with zero observed cross-device bleed. A real fix exists (the device already stores a `controlUid` data value with the actual target) but touches the most heavily live-tested code path in the whole app for a currently-theoretical risk; not worth the regression exposure. Documented in code, not silently left unaddressed.
- **GPT-07 (Medium) - WiFi signal is always labelled dBm using one unconditional formula, but LIFX documents two different encodings.** `parseWifiInfoPayload()` (`apps/LIFX_Light_Manager.groovy:1415-1424`) computes `10 * log10(signal) + 0.5` (confirmed against LIFX's own docs - this is the documented conversion, so the maths is correct) and always labels the result `dBm` (`apps/LIFX_Light_Manager.groovy:1292`), with no branch for LIFX's documented positive-value "quality band" (4-16+) or the `200` = "no signal" sentinel. Planned for 1.6.3.
- **GPT-08 (Medium) - an unrecognised LIFX product ID defaults to a full colour+CT light instead of the most conservative option.** `driverModeForProduct()` (`apps/LIFX_Light_Manager.groovy:3866-3875`) falls through to `"Switch + level + colour + CT"` for any unmapped product ID. That string then satisfies `driverTypeForRow()`'s `hasRealColour` substring match (`mode.contains("colour + ct")`, `apps/LIFX_Light_Manager.groovy:1847`), so an unknown device - which could be a future white-only product, or even a non-light LIFX Switch that rejects Light-capability messages entirely - gets classified as the Colour driver instead of `driverTypeForRow()`'s own genuinely-conservative fallback (White Mono, line 1860). Planned for 1.6.2.
- **GPT-09 (Medium) - a device removed from LIFX Cloud is never reconciled out of the saved table.** `mergeCloudIntoCurated()` (`apps/LIFX_Light_Manager.groovy:640-683`) only adds/updates rows present in the current Cloud response; nothing marks a previously `origin: cloud` row as stale/disconnected when it stops appearing in later responses. It stays counted as "expected" by `expectedCloudLanDiscoveryCount()` indefinitely, which can produce misleading missing-device counts and hold discovery open longer than it should. Planned for 1.6.3 - needs care to only trigger on a confirmed successful full Cloud fetch, not a partial/error response.
- **GPT-10 (Medium) - subnet discovery assumes a /24 network with no way to detect otherwise.** `hubSubnet()` (`apps/LIFX_Light_Manager.groovy:3942-3949`) derives only the first three octets of the hub's own IP via regex; Hubitat's app API doesn't expose the hub's actual subnet mask (confirmed via research), so true auto-detection isn't possible. Planned for 1.6.3: an optional manual subnet-prefix override preference, defaulting to today's exact `/24`-derived behaviour when left blank.

## Fixed, awaiting live-hub testing (1.6.1)

Three independently-verified findings from the same external review, all low-risk/mechanical:

- **GPT-01 (High) - a configured default level of 0% silently becomes 75%.** `deviceDefaultLevel()`/`deviceDefaultKelvin()` (`apps/LIFX_Light_Manager.groovy:2949-2963`) used `safeInt(v) ?: EFFECT_RESET_LEVEL`/`EFFECT_RESET_KELVIN` - Groovy's `?:` treats integer `0` as false, so a user who deliberately sets "Default level" to 0 got 75% instead whenever Off cancels an active Breathe/Pulse effect. The exact bug class this codebase has already fixed repeatedly elsewhere (`intOrDefault()`'s own comment two lines below explains precisely this footgun) - just not applied consistently here. Fixed: both now use `intOrDefault(v, fallback)`. Test plan: GPT01-01/02 in `TEST_PLAN_1.6.1.md`.
- **GPT-04 (Medium) - Master Switch aggregate state could go stale.** `refreshMasterSwitchMembership()` never touched the Master Switch's own `switch` attribute, so deleting the last active child could leave it showing `on` with `memberCount: 0`. The `LIGHT_STATE` response handler updated an individual child's switch state but never called `requestMasterStateReconciliation()`, while `LIGHT_STATE_POWER` right next to it did. Fixed: `refreshMasterSwitchMembership()` now also recomputes/publishes the aggregate `switch` using the same any-member-on semantics `groupChildRefresh()` already implements; `LIGHT_STATE` now reconciles the Master Switch too. Test plan: GPT04-01/02 in `TEST_PLAN_1.6.1.md`.
- **GPT-11 (Low) - "Clear saved discovery data" left some maintenance state behind.** `clearAllData()` reset five result fields but missed `atomicState.wifiCheckResult`/`backgroundMaintenanceResult`, and didn't cancel a pending `resendFirmwareCheck`/`resendWifiCheck` timer or reset their `*StartedAt` timestamps. Fixed: both result fields added to the reset list, both resend jobs explicitly unscheduled, both timestamps reset. Test plan: GPT11-01 in `TEST_PLAN_1.6.1.md`.

## Fixed, awaiting live-hub testing (1.6.0)

Already included in the 1.6.0 backport to `main` (see bottom section) before Gordon explicitly confirmed it live on `dev` - judged low-risk enough not to hold up the backport (a pure dead-code deletion), but still genuinely unconfirmed:

- **Removed the unreachable "rename an installed child device" backend, per Gordon's decision.** Follow-up to the 1.5.17 dead-code sweep's "Open — confirmed gap" finding. On review, this feature was functionally redundant with the already-working "rename discovered lights" UI (`renameDiscoveredLightsFromSettings()`, visible on the main page): that one already updates an installed device's real Hubitat label too, whenever a Discovery row still exists for it - `childCreationRows()` (what it iterates) depends on `atomicState.curatedRows`, whereas the unreachable feature's `managedLifxLightChildren()` queries Hubitat's installed devices directly, so the only case it uniquely covered was renaming a device after its Discovery row was gone (e.g. after "Clear saved discovery data"). Not worth restoring for that narrow case, so removed instead: `childRenameActionHtml()`, `childRenameSettingNameForDni()`, `renderChildRenameInputs()`, `childRenameSettingValue()`, `curatedRowsByChildDni()`, `renameManagedChildDevicesFromSettings()`, the `renameChildDevicesBtn` button dispatch entry, the "Child device rename" result-display section, and the `atomicState.childRenameResult` init/reset lines. App-file-only.

## Open — enhancement ideas

Feature/design suggestions, not bugs - not yet decided whether to pursue.

- **Master Switch bulk commands are genuinely sequential unicast, not broadcast - real "popcorning" risk on larger fleets.**
  `apps/LIFX_Light_Manager.groovy:2994-3011` (`sendFastUdpToIp()`): every bulk command loop sends one unicast UDP packet per device via `destinationAddress: "${row.ip}:${port}"`, confirmed not a single broadcast send. LIFX tagged broadcast packets would synchronize the whole fleet's transition instead of a visible ripple. Trade-off worth weighing before pursuing: this app already caused one real hub crash from LAN traffic overload earlier in development, with substantial pacing work done since specifically to avoid a repeat - a tagged broadcast packet is processed by *every* LIFX device on the LAN, not just this app's managed ones, a different reliability/rate profile than the current tuned-against-a-real-incident approach.

- **No proactive offline/health detection - a device that stops responding is never flagged.**
  No offline/presence/unresponsive handling exists anywhere in the app. `pollManagedChildSwitchStatus()` (`apps/LIFX_Light_Manager.groovy:2413-2443`) sends `GET_POWER` on a schedule and updates state only when a response arrives; there is no timeout-based negative case, so a bulb powered off at the wall keeps showing its last-known state indefinitely. The existing "optional lightweight LAN polling" feature sounds similar but only covers the success path.

Checked and not added: "advanced capability extension" (multizone/Tile/Beam/waveforms) is already a declared limitation in `README.md`. "Custom transition times" was factually wrong as a suggestion - already implemented end to end via `setLevel(value, duration = 0)`, `setColorTemperature(value, level = null, duration = 0)`, and `setColor(Map value)` (reading `value?.duration`) on every local driver.

Not yet verified from the ChatGPT re-review (vaguer, no code citations checked): "metadata not consistently persisted," "some events emitted for unsupported capabilities," "edge case where Master state may not reconcile." Its Architecture Observations (state-heavy design, no canonical identity model, discovery modes not properly separated) are design-quality opinions in the same category as the already-declined E-01-E-12 items below, not concrete bugs.
